# VideoDB boundary

The trusted-process service in `src/engine/videodb/` is separate from the engine's renderer-facing state surface. `npm start` runs the real state engine. A packaged app uses the production API. The integration plan and SDK handoff are canonical in [Bloom's architecture tracker](https://github.com/Spext/architectures/blob/main/Products/Bloom/docs/trackers/integration-v1.md).

## Construction

Call `createVideoDBBoundary` from Electron main after `app.whenReady()`. Pass Bloom's own data directory; never the folder used by releases up to 2.3.0. Construction loads dependencies and any operation journal but performs no network requests, launches no capture process and requests no permissions.

```javascript
const { app } = require('electron');
const { createVideoDBBoundary } = require('./src/engine/videodb');

app.whenReady().then(() => {
  const service = createVideoDBBoundary({
    dataDir: app.getPath('userData'),
    apiUrl: 'https://api.dev.videodb.io',
  });
});
```

The service constructor defaults to development. Production can be explicitly selected with `https://api.videodb.io`; arbitrary origins are rejected. Each environment has its own credential and operation files under `videodb-dev/` or `videodb-prod/`. The SDK is installed as `videodb-capture` from `github:video-db/videodb-node`, pinned in `package.json` to one commit on the release-0.3.3 branch. The SDK recorder adapter uses public CaptureClient lifecycle APIs, not the native development wrapper. HLS playback code is bundled as the hls.js dependency; no player code is loaded from a CDN.

## Public operations

| Method | Contract |
|---|---|
| `signIn(apiKey)` / `restore()` | Validate through collection discovery before saving local credentials or replacing the active scope. A failed connection preserves the previous scope. Return non-secret scope and collection identifiers; never return the key |
| `signOut()` | Remove the saved credential and invalidate delayed reads. Pending or uncertain mutations block sign-out/account switching |
| `ensureCollection()` | Explicitly create a private Bloom Recordings collection only when missing. Sign-in and library browsing do not create one |
| `listRecordings()` / `getPlayback(id, collectionId?)` | Use the bound Bloom collection, or for `getPlayback` another collection of the same account when one is named; return projected metadata and validated HTTPS playback/thumbnail URLs. Existing thumbnail metadata is displayed without generation; missing or failed images keep the placeholder. No indexing or generation is triggered |
| `usage()` / `listCollections()` / `listCollectionVideos(id)` | Read-only views of the account: the credit balance, every collection by id and name with Bloom's own marked, and one collection's videos in the same projection. Videos from another collection are browsed read-only: the engine marks them and refuses rename, delete and transcript requests for them |
| `renameCollection(id, title)` / `deleteCollection(id)` / `reconcileCollectionAction(id)` | Rename preserves the existing description; deletion removes the collection and its media after UI confirmation. Mutations are journalled and uncertain outcomes require reconciliation. The bound Bloom recording destination is protected from rename/delete and its name is reserved. An uncertain deletion remains in the sidebar until confirmed, including after restart |
| `search(query)` | Semantic search over the spoken index of the bound Bloom collection through the SDK's legacy search; returns video id, start, end and the spoken text. An empty answer is an empty list. Covers only recordings that have been transcribed. The SDK's newer search and `ask` need indexes Bloom does not create |
| `rename(id, title)` / `deleteRecording(id)` | Persist an operation receipt before mutation, serialize conflicting mutations and resolve only on acknowledgement |
| `pendingOperations()` | Return safe pending operation descriptions for recovery UI |
| `reconcileRecording(id)` / `reconcileCollection()` | Read remote evidence. Clear an uncertain rename only if its intended title matches, a delete only on confirmed absence, and collection creation only on one unambiguous matching collection. An unmatched read is not permission to replay |
| `transcript(id, collectionId?)` | Read text and word timestamps without indexing. Playback and transcript reads are independent; failed or empty refreshes retain cached transcript text and paragraph timings. Accepted indexing is remembered locally so Try again only reads the result. Empty text is `empty`, not proof of no speech; malformed or failed responses are errors |
| `summarise(paragraphs)` | Generate a short title, summary, key points and action items from transcript paragraphs with their start times, through the collection's text generation in JSON mode. Returns only validated text, with each point's time kept only when it falls inside the recording. Sends at most 24,000 characters of transcript |
| `requestTranscript(id)` | Explicitly request spoken indexing, check `success:true`, and retain a confirmed receipt to deduplicate requests across restart. Uncertain indexing is not automatically retried |
| `prepareDownload(id)` | Return a validated HTTPS download URL and safe filename. The host still owns the save dialog and actual file transfer |
| `makeVersion({ videoId, ranges, subtitles, title, titleStyle, endText })` | Ask VideoDB's editor once for a new stream made of the kept ranges; see [Making a version](#making-a-version) |
| `uploadRecording({ path, title })` | Send a finished recording's video to the Bloom collection; see [Recording](#recording-standalone-mode) |
| `createSession(operationId)` / `ownsSession(id)` / `recorderToken({ sessionId })` / `reconcileSession()` | Kept from the session-backed recorder. Recording has used no session or token since standalone mode (ADR 0005); only `reconcileSession` is still called, to clear an uncertain creation left by an earlier build |
| `captureCapabilities()` | Report missing public lifecycle methods. Reject a client without `startLocalRecording`, `stopLocalRecording` or `getWindows` |

Duplicate Bloom collection names are rejected instead of silently selecting a collection. Keys and environments have separate internal scope fingerprints; a rotated key gets an isolated scope and requires a remote library refresh. These fingerprints do not establish a stable cross-key VideoDB account identity.

## Persistence and errors

`credentials.json` holds a versioned local API key record without encryption at rest, per the owner’s internal-build storage decision. No Keychain API is called. The earlier `key.enc` file is ignored: enter the key once after updating. Sign-out removes both credential files. `operations.json` contains a versioned allowlisted set of operation identities, intended rename titles and confirmation states, never credentials, media URLs or raw SDK responses. Writes use unique temporary files, restrictive permissions, file sync, directory sync on platforms supporting it, and atomic rename. `library.json` caches allowlisted recording fields and marks separately; media paths and playback URLs are excluded. Corrupt library data is copied aside before rebuilding from cloud recordings and native jobs. Corrupt files are retained and reported; they are not silently reset. This journal does not replace the native recorder's media/relay journal.

The default host request deadline is 30 seconds. A deadline ends the host wait, not the SDK request or a remote mutation. Uncertain mutations remain in the journal and are not replayed automatically. Confirmed indexing receipts survive restart. Uncertain indexing/session mutations without sufficient remote evidence remain pending for explicit recovery handling; a service caller must not display a generic Retry that resubmits them.

Errors crossing the service boundary use safe `code`, `message` and `uncertain` fields and omit SDK messages, causes, headers and URLs. Playback and download URLs are main-process transient results, not journal content. The host validates IPC senders and payloads, projects service results into engine state, and supplies the renderer with allowed actions; no renderer imports this module or the SDK.

Run `node --test src/tests/videodb-service.test.js` for fake-SDK checks of collection isolation, acknowledgement, timeouts, late-result reconciliation, restart receipts, account switching, credential persistence and permissions, corruption and safe error mapping. These tests make no network requests and start no capture. `videodb-engine.test.js` verifies the capture state machine, source exclusion, pause timing, recovery and shutdown against a fake recorder; `local-recorder.test.js` verifies the SDK adapter, and `make.test.js` the cut plan, the editor call and versions. `app-ui.cjs light` and `dark` verify the views with the real engine on a fake service and recorder, with external media requests blocked. The --fixture mode is ignored by packaged builds. `node --check` applies to every module in this boundary. Installed binary checks and real recording/playback acceptance are separate evidence in the architecture tracker.

## Recording (standalone mode)

Since 14 Nov 2026 Bloom records in the SDK's standalone mode (architecture ADR 0005). `local-recorder.js` is the only file that calls the SDK's recorder. Start is `startLocalRecording` with no backend session, token or live streams, so nothing is asked of VideoDB before capture begins; Stop finalises a local MP4. The adapter then sends the file to the Bloom collection through `service.uploadRecording({ path, title, onProgress })` and reports the outcome to the engine as `recording-progress` (whole percent), `processing-complete` or `recording-relay-failed` with `permanent` true only when the file is gone. `uploadRecording` does not use the SDK's `uploadFile`, whose client gives each request 60 seconds: it asks for the collection's upload address, streams the file there itself with no request time limit and redirects off (following redirects buffers the whole file in memory), gives up only when nothing has moved for two minutes, then registers the video with the same call as the SDK's `uploadURL`, through the SDK's client but waiting up to an hour for VideoDB to make the video (the SDK's own wait is about eight minutes, after which the file would be sent again). While a file is being sent, `src/main/keep-awake.js` holds Electron's `prevent-app-suspension` power-save blocker so the Mac does not idle-sleep; closing the lid still interrupts the send. The engine tries a recording the connection let down again after 1, 5 and 15 minutes, then every 30, and at every launch. It keeps `local-recordings.json` beside the other engine files: one entry per recording with its account, file path, stage and video id. File paths stay in that file and in the main process; the engine and windows see ids only. After a restart the list is how an unfinished file is found and sent again, for the account that made it only. Sending does not depend on the recorder, so an earlier recording keeps being processed while a new one is captured. Sound comes from the Mac's default microphone and system audio only; there is one video source. The local file is kept after it is in VideoDB; removing it is an open product decision. A recording that failed under the earlier session-based recorder is not in this list and cannot be recovered by this build.

The camera is not a recorder source. `setCamera` only sets `sources.camera`; `src/main/floating.js` then shows Bloom's own round window with the camera's picture, which a display recording contains because it is on that screen and a window recording does not. The SDK is never asked for a camera.

A recording's file, and the recorder's folder for it, are deleted once the recording is confirmed playable (sent, a video id returned, a stream link read back), and its entry is dropped from `local-recordings.json` (ADR 0006); a recording not yet confirmed keeps its file so it can be sent again. A Start the recorder answers with a refusal returns the engine to idle with nothing left behind; a Start that gets no answer leaves it in `stopped` until Stop, which ends in idle when the recorder says nothing was being recorded. A recording whose Stop never answered has no file on record; Recover looks for a finished one where the recorder keeps them before calling it unrecoverable. Recover never sends a recording that is already in VideoDB.

Verified against the dev API on 14 Nov 2026 with a generated four-second file: sent, playable and named in 36 s, then deleted. Not yet verified with a real capture, because the test Mac's screen was locked; see the runbook's recorder check.

## Making a version

`make.js` works out, from the transcript's word timings, the stretches of 0.8 s or more where nothing is said (kept with the recording as `quiet`) and the ranges a version keeps. `editing.js` is the only code that calls VideoDB's editor: an `EditorTimeline` with one video track of the kept ranges, a `CaptionAsset` with `src: 'auto'` for subtitles, and an `EditorTextAsset` over the first 2.5 s for the title. The title is one of three: over the first 2.5 s in a boxed text clip (the one style rendered so far), an opening card (text alone for 3 s on the timeline's background colour, with the video, subtitles and everything else starting after it), or a lower third (a smaller boxed text clip anchored `bottom_left` with a relative offset, for 4 s). An end card is text alone for 3 s after the last clip. Tracks are added video, subtitles, titles, because later tracks draw above earlier ones. A clip's length is cut to the hundredth of a second and never rounded up, since VideoDB refuses a clip longer than its source. Fonts are VideoDB's default, Clear Sans; it offers no other Latin family. `generateStream` is asked once with a 15-minute deadline and never repeated automatically. The result is a stream and player link in VideoDB; the recording's own video is not touched. `make-commands.js` keeps each version (name, links, length, the cuts it made, its chapters) in the recording's `versions`, which live only in this Mac's `library.json`: VideoDB has no record that a stream belongs to a recording, so another Mac shows the original alone. Editor output carries a VideoDB watermark on the accounts tried so far.

Verified with a fake editor and a fake service only. The editor calls are the ones run by hand on the dev API on 13 Nov 2026 (see the architecture gaps page, experiment (b)); the app's own path has not yet made a real version.

## Engine and renderer integration

`engine.js` owns application state and emits cloned snapshots through getState/onState. Validated command acceptance does not mean asynchronous work succeeded; confirmed outcomes appear in state. `access.js`, `capture.js`, `jobs.js` and `library-commands.js` own account orchestration, capture transitions, native-job recovery and recording actions respectively. `collection-actions.js` owns journalled collection mutations and reconciliation. `explore-commands.js` owns what the app shows about the account beyond its own recordings: collections, the balance, the collection being browsed and the last search. `understand-commands.js` owns a recording's summary, and `paragraphs.js` turns word timings into the paragraphs both the transcript view and the summary use. VideoDB times each word as `{ text, start, end }` and marks silences with `-`; the service drops the markers. The SDK-specific calls and event names live only in `recorder.js`. The renderer modules never import the SDK or receive credentials, native paths or raw event payloads.

This release includes API-key sign-in, OS permission rechecks, a choice of display or single window, the default microphone and optional system audio, Start/Pause/Resume/Stop, muting a sound source while recording, marks, recovery of a recording whose processing failed, cloud playback, links, transcripts, summaries with chapters, versions made from a recording, rename/delete/download, settings and readiness notifications. Capture asks nothing of VideoDB at start, uses one video source and optional audio, and sends the finished MP4 as the final video. No server-storage fallback is introduced. An earlier recording never blocks a new one (ADR 0004 in the architecture decisions): Start is available as soon as the last recording's file is on this Mac, shown by its recorder id, and an earlier recording goes on being processed while the next is made.

Quitting asks first only while Bloom is capturing or the file is still being written; the engine then awaits Stop before suspending the recorder. In every other state, including a recording being processed or needing recovery, Bloom quits without a question: it gives the recorder four seconds to suspend and otherwise ends the recorder process through `recorder.abandon()`, the one place the adapter reaches past the public SDK, so the recorder never outlives the app. Retained jobs are discovered at the next launch, which does not wait for that recovery. The current native format does not guarantee recovery of an unfinished MP4 after a forced process kill. Opening the app never starts capture automatically; recording requires its Start action. Live transcript and meeting detection are not part of this release.
